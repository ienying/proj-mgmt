# 案例中心 提示词

## 角色

你是教育信息化客户画像结构化建模工程师。负责搭建「案例中心」——包含用户画像（单客户深度）和产品案例（跨项目聚合）两大功能。面向学校客户，公司提供智慧校园整体解决方案，覆盖管理、教学、德育、安防、局端对接、物联网硬件等 101 个产品模块。

---

## 一、系统定位

案例中心是项目管理系统的**独立顶级模块**，在 Dock 导航栏上以独立图标呈现，与「项目管理」「任务中心」「客户管理」等模块平级。

```
Dock 导航栏
  项目管理 │ 任务中心 │ 客户管理 │ 案例中心 │ ...
                          │
                    ┌─────┴─────┐
                  用户画像    产品案例
                  (单客户)    (跨项目聚合)
```

- **用户画像**：从客户科室出发，逐科调研业务 → 匹配适用模块 → 追踪落地效果
- **产品案例**：以模块为维度，跨学校聚合使用案例和素材

**数据流**：工程师访谈各科室 → 录入科室业务 + 匹配模块 → 已落地模块上传素材 → 产品案例自动跨项目聚合

**系统边界**：

| ✅ 允许 | ❌ 禁止 |
|--------|--------|
| 新建独立 Schema `design_case_center` 存放所有表 | 修改已有功能代码、表结构、业务逻辑 |
| 新增案例中心相关接口、页面、Dock菜单项 | 改动已有项目、客户、任务等数据表 |
| 读取项目基础数据自动同步 | — |

## 二、用户画像

### 2.1 画像核心思路：科室 → 模块

画像是从客户内部视角出发的。不按产品线罗列模块，而是从学校各科室的实际业务入手：

```
科室走访 → 了解该科室日常做什么、怎么做的、痛在哪
       → 匹配哪些模块能解决这些痛点 / 已在使用哪些模块
       → 记录每个模块的真实使用情况
       → 画像 = 所有科室的汇总全景
```

### 2.2 科室与模块对照关系

一个模块通常由**一个主要科室**主导，但同时需要**多个科室协同配合**。画像需要记录每个模块的多科室关系。

| 科室 | 日常核心业务 | 主要使用的模块 | 参与协同的其他科室 |
|------|-------------|--------------|------------------|
| **校领导** | 全校数据总览、决策支持、审批 | 数据大屏/驾驶舱、流程审批、数据可视化 | — |
| **教务处** | 排课、考务、成绩、巡课、教学质量 | 课表中心、考务管理、成绩管理、在线巡课、教学质量、基础教务 | 教研室（教研数据）、信息中心（系统运维） |
| **教研室** | 教研活动、集体备课、资源建设、课题管理 | 集体备课、网络教研、资源中心、科研项目、知识库 | 教务处（课表对接）、信息中心（平台运维） |
| **学生处/德育处** | 德育评价、班级管理、综合素质、行为规范 | 德育管理、班级评价、综合素质、特殊学生库、学生请假 | 宿管科（宿舍行为）、保卫处（进出校记录）、心理中心（心理数据）、年级组（班级管理） |
| **信息中心** | 系统运维、数据管理、账号管理、平台对接 | 基础数据中心、认证管理、数据开放、表单管理、所有第三方对接、流程管理 | **所有科室**（账号/权限/数据支持） |
| **人事处** | 教师档案、考勤、薪资、职称评定 | 人事管理、教师档案、教师考勤、薪资管理 | 教务处（教师课时统计）、财务处（薪资发放） |
| **财务处** | 学费收缴、工资发放、经费管理 | 网上收费、薪资管理、缴费管理 | 人事处（薪资数据）、学生处（学生名单） |
| **后勤/资产处** | 资产管理、耗材采购、教室场地管理 | 资产管理、耗材管理、空间预约、食堂管理 | 信息中心（设备资产）、教务处（教室使用） |
| **保卫处** | 进出校管理、访客登记、安防监控 | 进出校管理、访客管理、视频融合、在线巡查 | 学生处（请假审批联动）、宿管科（归寝联动）、年级组（学生管理） |
| **招生办** | 招生宣传、报名录取、新生报到 | 招生管理、迎新报到 | 信息中心（数据同步）、财务处（缴费） |
| **就业处/实习办** | 实习安排、校企对接、毕业去向 | 实习管理、毕业去向 | 教务处（学分对接）、学生处（学生档案） |
| **督导室** | 教学督导、听评课、质量评估 | 督导评估、教学督导、教师评价 | 教务处（课表/成绩）、教研室（教研数据） |
| **心理中心** | 心理咨询、心理普查、危机干预 | 身心健康、特殊学生库 | 学生处（学生信息）、年级组（班主任反馈） |
| **宿管科** | 宿舍分配、查寝、归寝管理 | 宿舍管理、人脸面板机/宿舍牌 | 学生处（学生信息/请假）、保卫处（进出校）、年级组（班主任查寝） |
| **校办** | 公文流转、会议管理、OA审批 | OA办公、公文管理、会议管理、任务协同 | **所有科室**（公文/流程发起方） |
| **年级组/学院** | 年级管理、班主任工作、班级主页 | 班级主页、家校通知、学生档案、综合考勤、晨午检 | 学生处（学生管理）、教务处（成绩）、宿管科（归寝） |

> 上表是典型对照关系，实际以走访结果为准。**信息中心和校办是天然的全校协同节点**——所有科室都会通过它们使用系统或发起流程。

### 2.3 多科室协同模块的处理规则

当一个模块涉及多个科室时：

| 场景 | 处理方式 |
|------|---------|
| **录入时** | 模块归属到**主要使用科室**下填写，在「协同科室」字段勾选其他参与科室 |
| **查看时** | 该模块在主要科室详页中完整展示，在协同科室详页中以「协同参与」标签简化展示 |
| **编辑时** | 修改该模块状态，主科室和协同科室视图同步更新（同一份数据） |
| **统计时** | 模块只计入主要科室的计数，避免重复计算 |

**前端示意**——宿舍管理模块在宿管科（主要科室）中完整展示，在学生处和保卫处中简化展示：

```
【宿管科 Tab — 完整展示】
  ✅ 宿舍管理  ·  使用率 90%  ·  活跃用户：52人
  协同科室：学生处(学生信息共享)、保卫处(归寝联动)、年级组(班主任查寝)
  ─────────────────────────────────────
  落地效果：归寝核查效率提升80%...
  [📎 素材：3个文件]

【学生处 Tab — 简化展示】
  ─ 协同模块 ─
  ✓ 宿舍管理（协同） · 主科室：宿管科 · 学生信息已对接 → [跳转到宿管科]

【保卫处 Tab — 简化展示】
  ─ 协同模块 ─
  ✓ 宿舍管理（协同） · 主科室：宿管科 · 归寝数据已联动 → [跳转到宿管科]
```

### 2.4 画像录入/编辑

画像支持三种更新路径，不同路径适用于不同场景：

| 路径 | 入口 | 适用场景 | 操作内容 | 触发版本 |
|------|------|---------|---------|---------|
| **新建画像** | 列表页「+ 新建画像」→ 空白表单 | 首次为学校建档 | 全量填写基础信息+硬件+科室业务+模块状态 | v1 |
| **直接编辑画像** | 详情页「编辑」按钮 → 预填充表单 | 定期更新（如一个季度后重新走访科室、模块落地状态变更） | 修改任意字段：科室人员/业务/痛点、模块状态/使用率、硬件网络、素材 | v2, v3, v4... |
| **周报录入** | 详情页「本周周报」→ 周报表单 | 日常运维记录 | 每日工作、巡检、宣传、新认知、反馈、问题 | 每次提交生成版本 |

**三者的关系**：
```
新建画像 ──→ 直接编辑 ──→ 直接编辑 ──→ ... (每次生成版本)
               │           │
               └── 周报 ──→ 周报 ──→ 周报 ──→ ... (每次提交生成版本)
```

- 周报是**日常增量**：每周追加工作记录、小范围模块进展
- 直接编辑是**阶段性全量**：季度回访后一次性刷新科室业务描述、批量更新模块状态
- 两者互补：周报数据积累一段时间后，工程师通过直接编辑把周报中的重要变化固化为画像字段

**直接编辑的关键交互**：
- 详情页每个科室 Tab 右上角有「编辑此科室」按钮，支持按科室单独编辑（不一定要改全部）
- 也可通过「编辑画像」进入全量编辑页面（所有科室在同一页）
- 编辑保存后自动生成版本记录，标注修改了哪些科室、哪些模块

### 2.4.1 新建/编辑表单布局

单页表单（类似新建项目页面），从上到下按科室走访顺序排列：

- **基础信息**：学校类型自动带出，所有字段在顶端，硬件/网络放在基础信息区内
- **科室业务表单**——每个科室一个折叠面板，按 2.2 表排序，打开后填写：

```
科室负责人：姓名 | 职务 | 联系方式
日常核心工作：___
业务流程（他们怎么做的）：___
当前痛点：___
在用工具/系统：___
信息化期望：___

▼ 模块匹配（基于该科室业务自动推荐的模块，工程师逐项评估）
  [模块A] 状态：✅已落地/⚠️未落地/🔴未购  |  使用率___%  |  活跃用户___  |  效果___  |  问题___
           协同科室（勾选）：□教务处 □学生处 □保卫处 □信息中心 □宿管科 □年级组 □校办 □...
  [模块B] 状态：...
  [+ 手动添加模块]
```

- **产品素材**：已落地模块右侧「📎」按钮上传视频/PPT/文字介绍

**按键交互**：底部固定操作栏「保存草稿」+「提交」。编辑时数据预填充回显。

### 2.5 为什么这样设计

科室走访 → 模块匹配 的核心优势：

1. **工程师调研有路径**：不需要面对 101 个模块列表发懵，而是按科室一个一个走，自然覆盖所有模块
2. **业务驱动而非产品驱动**：先理解客户在做什么，再匹配产品，而不是反过来让客户理解我们的产品线
3. **遗漏自检**：每个科室匹配完模块后，如果某个科室没配任何模块，说明这个科室的业务可能还没被我们的产品覆盖

### 2.7 周报录入

**周报 vs 直接编辑**：

| | 直接编辑画像 | 周报录入 |
|------|------------|---------|
| 改什么 | 科室业务描述、模块状态/使用率、硬件等主字段 | 每日工作、巡检、宣传、新认知、问题、计划 |
| 影响范围 | design_customer 主字段直接更新 | 追加到 weekly_reports JSON 数组 |
| 是否生成版本 | ✅ 每次编辑生成版本 | ✅ 每次提交生成版本 |
| 频率 | 季度/半年度阶段性更新 | 每周 |

周报是画像的**活水来源**——日常积累。当周报中反复出现某个模块的使用率变化或科室新需求时，工程师应通过"直接编辑"将这些信息正式更新到画像字段中。

**周报表单结构**（单页，滚动填写）：

| 板块 | 内容 | 字段类型 |
|------|------|----------|
| 诚信声明 | 确认记录真实 | 勾选框 |
| 每日工作 | 逐日记录（__日）：工作内容，含培训、试点、案例拍摄 | 多行文本，按日分组 |
| 巡检维护 | 巡检时间/范围/隐患/是否上报处理 | 表单+下拉 |
| 应用落地宣传 | 宣传主题(模块)/图片视频/说明 | 文本+文件上传（有就传，没有填未提交原因） |
| 了解客户业务 | 科室/人员/职务/核心业务/产品适配/效果反馈 | 下拉+文本 |
| 市场贡献 | 线索来源/线索内容/对接建议 | 下拉+文本 |
| 未解决问题 | 问题描述/滞留原因/处理思路 | 动态表格 |
| 下周计划 | 计划条目+总部支持需求 | 多行文本 |

**周报去重**：同学校+同工程师+同周报周期只保留一份，重复弹窗确认覆盖。

**关键词**：日清日结 · 有图有真相 · 问题闭环 · 下周计划可追踪

**去重规则**：同学校+同工程师+同周期只保留一份，重复弹窗确认覆盖。

## 四、学校类型适配

### 4.1 作用

不同学校类型的业务场景差异巨大。学校类型适配决定了**哪些科室和模块对该校有意义**：

1. **减少无效工作**：自动隐藏不相关的内容，工程师精力集中在有意义的科室和模块上
2. **提升数据质量**：聚焦该类型学校的核心科室，确保关键数据不遗漏
3. **画像可比性**：同类型学校才有对比意义

### 4.2 科室差异

| 类型 | 缺失/弱化的科室 | 额外/强化的科室 |
|------|----------------|----------------|
| 小学 | 宿管科、招生办、就业处、督导室 | 家校共育（强）、心理中心（强） |
| 初中 | 招生办、就业处、督导室 | +宿管科、德育处 |
| 高中 | 招生办、就业处 | +考务（强）、成绩分析（强）、督导室 |
| 中职 | —（全科室） | +招生办（强）、就业处/实习办（强）、实训室（强） |
| 高职 | —（全科室） | +科研（强）、就业处（强）、教研室（强） |
| K12 | 招生办、就业处、督导室 | 小学+初中合并 |

### 4.3 前端操作

**录入时**：
- 选学校类型后，科室列表和模块推荐自动调整——不存在的科室不展示，不适用模块不推荐
- 硬件区域联动：小学自动隐藏宿舍楼栋相关字段；中职额外展示实训室字段

**查看时**：
- 不适用科室不出现，不适用模块灰色标注跳过
- 产品案例筛选按学校类型自动过滤

**编辑时**：
- 学校类型不可修改（类型变更=重新建档）

## 六、版本历史

画像支持版本管理，核心目的是**跟踪学校信息化建设的变化趋势**——例如"半年前该学校只有 5 个模块落地，现在增长到 18 个，信息化等级从初级升至中级"。

每次编辑或周报提交后生成一条记录，存入 `profile_versions` 表：

```
id | profile_id | version_num | changed_fields(JSON) | diff_summary | operator | created_at
```

**趋势分析**：
- 时间轴查看 v1→vN 全链路演变
- 等级变化节点追踪
- 模块增长曲线（通过版本 diff 绘制）
- 点击版本展开变更前后对比

### 调研表与周报在画像中的数据流向

```
调研表（一次性）
  ├─ 基础信息 + 硬件网络 → 画像基础字段
  ├─ 信息化系统建设情况 → 模块状态初始填充
  ├─ 实地勘察 → 硬件/场地字段
  └─ 科室需求 + 走访记录 → 科室业务字段 + 模块匹配

周报（每周持续）
  ├─ 每日工作 + 巡检 → 运维记录，累积到 weekly_reports
  ├─ 应用落地宣传 → 宣传记录（可作为素材补充）
  ├─ 了解客户业务 → 科室业务补充认知，驱动画像字段更新
  ├─ 市场贡献 → 线索记录（助工程师回顾，非画像核心数据）
  └─ 问题 + 计划 → 问题追踪，下周计划

## 十、规则汇总

**核心思路**：科室走访 → 业务理解 → 模块匹配 → 落地追踪 → 画像成型

**数据规则**：单客户单表 · 项目数据自动同步 · 新建全量/编辑增量 · 空值默认「未采集」· 字段溯源标注 · 学校类型过滤科室和模块

**调研表规则**：一次录入覆盖学校全貌 · 基础信息+硬件勘察+信息化系统+科室走访 · 实地勘察细节(大门宽度/AI终端空间/监控拾音)不容省略

**周报规则**：每日记录（非周汇总）· 同周期去重确认覆盖 · 有图有真相 · 问题闭环 · 每次提交生成版本

**素材规则**：仅已落地可上传 · 每模块最多3件 · 降级自动删除 · 提示确认 · OSS存储

**素材规则**：仅已落地可上传 · 每模块最多3件 · 降级自动删除 · 提示确认 · OSS存储

**周报规则**：同周期去重 · 确认覆盖 · 不触发版本历史

**版本规则**：每次编辑或周报提交均生成版本 · 保留全量历史 · 变更前后对比 · 趋势追踪 · 周报版本标注操作类型(编辑/周报)

**产品案例规则**：不新增存储 · 从画像聚合查询 · 降级自动失联 · 支持筛选/统计/对比/导出

**禁止事项**：不碰已有代码和表 · 独立 Schema `design_case_center` · 不删调研字段 · 不做销售分析 · 不覆盖历史数据

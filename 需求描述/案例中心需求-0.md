# 案例中心 提示词

## 角色

你是教育信息化客户画像结构化建模工程师。负责搭建「案例中心」——包含用户画像（单客户深度）和产品案例（跨项目聚合）两大功能。面向学校客户，公司提供智慧校园整体解决方案，覆盖管理、教学、德育、安防、局端对接、物联网硬件等 101 个产品模块。

---

## 一、系统定位

案例中心是项目管理系统的**独立顶级模块**，在 Dock 导航栏上以独立图标呈现，与「项目管理」「任务中心」「客户管理」等模块平级。

```
Dock 导航栏
  项目管理 │ 任务中心 │ 案例中心 │  │ ...
                          │
                    ┌─────┴─────┐
                  用户画像    产品案例
                  (单客户)    (跨项目聚合)
```

- **用户画像**：从客户科室出发，逐科调研业务 → 匹配适用模块 → 追踪落地效果
- **产品案例**：以模块为维度，跨学校聚合使用案例和素材

**数据流**：工程师访谈各科室 → 录入科室业务 + 匹配模块 → 正式使用/试用中模块上传素材 → 产品案例自动跨项目聚合

**系统边界**：

| ✅ 允许 | ❌ 禁止 |
|--------|--------|
| 新建独立 Schema `design_case_center` 存放所有表 | 修改已有功能代码、表结构、业务逻辑 |
| 新增案例中心相关接口、页面、Dock菜单项 | 改动已有项目、客户、任务等数据表 |
| 读取项目基础数据自动同步 | — |

### 1.1 全局 UI 设计原则

案例中心整体风格定位为**数据看板（Dashboard）**，而非传统管理后台列表页。核心要求：

**视觉层级（信息密度高、一眼抓住重点）**：
- 每个卡片/模块必须有**视觉权重**：用颜色（绿/蓝/黄/灰）、左边框色带、进度条、数字大字体区分重要程度
- 数据指标用**大号数字 + 小号标签**，卡片底色浅灰/浅色微区分，不要大面积白底
- 顶部核心指标卡使用**彩色图标 + 深色数字**，类似 BI 看板的 KPI 卡片

**配色方案**：
- 主色：`#4f46e5`（靛蓝），用于主按钮、选中态、链接
- 成功/正式使用：`#16a34a` 绿色系
- 试用/推广中：`#2563eb` 蓝色系
- 已购未用/警告：`#ca8a04` 黄色系
- 未购/禁用：`#d1d5db` 灰色系
- 背景：`#f3f4f6` 浅灰，卡片：`#fff` 白色

**布局规则**：
- 左侧深色固定侧边栏（220px），顶部面包屑栏（56px 固定），内容区滚动
- 卡片间距 16-20px，圆角 10px，轻微阴影
- 状态徽章统一使用圆角胶囊形状（pill badge）

**交互规则**：
- 悬停状态：卡片上浮阴影加深、表格行变色、按钮微变色
- 模块卡片：左边框 4px 色带区分状态（绿/蓝/黄/灰）
- 进度条：高度 6-8px，圆角，填充分色

**响应式**：
- 小屏幕侧边栏折叠为图标模式（60px）
- 统计卡片网格自动换行（最小 200px 每列）

## 二、用户画像

### 2.1 画像核心思路：科室 → 模块

画像是从客户内部视角出发的。不按产品线罗列模块，而是从学校各科室的实际业务入手：

```
科室走访 → 了解该科室日常做什么、怎么做的、痛在哪
       → 匹配哪些模块能解决这些痛点 / 已在使用哪些模块
       → 记录每个模块的真实使用情况
       → 画像 = 所有科室的汇总全景
```

### 2.2 多校区管理

很多学校有多个校区，管理模式各不相同。画像需要适配三种校区管理模式：

| 模式 | 特征 | 典型例子 | 画像处理 |
|------|------|---------|---------|
| **单校区** | 只有一个校区 | 大多数县城中学 | 标准画像，不启用校区概念 |
| **多校区独立** | 各校区独立管理，人事/教务/后勤各自分开 | 集团化办学、一校多区独立运营 | 每个校区一份完整的科室+模块数据，互不影响 |
| **多校区交叉** | 部分部门（如信息中心、校办）全校统一，部分（如教务处、学生处）分校区分开 | 总校+分校 / 本部+新校区 | 全校统一部门只填一次并标注「全校共享」；分校区的部门逐个校区填写 |

**常见交叉场景**：

```
株洲市二中（本部+初中部+附小）
  ├── 全校共享：校领导、信息中心、校办、财务处（统一管理）
  ├── 高中部独立：教务处、教研室、学生处、年级组（高中学段专属）
  ├── 初中部独立：教务处、教研室、学生处、年级组（初中学段专属）
  └── 附小独立：教务处、教研室、学生处（小学学段专属）
```

**前端交互——校区模式选择**：
- 建画像时，先选「校区模式」：单校区 / 多校区独立 / 多校区交叉
- 选多校区后，弹出校区列表配置面板：校区名称、学校类型（不同校区可能类型不同，如本部高中+分校初中）、学校地址
- 每个校区的教学楼、宿舍、食堂、监控等硬件独立填写
- 科室填报时：
  - 全校共享的科室 → 出现一次，标注「全校共享」
  - 分校区科室 → 每个科室右上角下拉选「所属校区」，不同校区同一科室可分别填写

**数据库设计**：
- `campus_mode` 字段：single / multi_independent / multi_cross
- `campuses` JSON 数组：[{name, type, address, hardware:{...}}]
- 科室字段新增 `dept_scope`：school_wide（全校共享）/ campus_specific（校区专属）
- 校区专属科室字段新增 `campus_id` 指向对应校区

**产品案例中的校区处理**：
- 产品案例按模块聚合时，一个学校的多校区数据汇总为一个学校展示
- 可选展开查看各校区的模块落地情况（如高中部正式使用、初中部试用中）

一个模块通常由**一个主要科室**主导，但同时需要**多个科室协同配合**。画像需要记录每个模块的多科室关系。

| 科室 | 日常核心业务 | 主要使用的模块 | 参与协同的其他科室 |
|------|-------------|--------------|------------------|
| **校领导** | 全校数据总览、决策支持、审批 | 数据大屏/驾驶舱、流程审批、数据可视化 | — |
| **教务处** | 排课、考务、成绩、巡课、教学质量 | 课表中心、考务管理、成绩管理、在线巡课、教学质量、基础教务 | 教研室（教研数据）、信息中心（系统运维） |
| **教研室** | 教研活动、集体备课、资源建设、课题管理 | 集体备课、网络教研、资源中心、科研项目、知识库 | 教务处（课表对接）、信息中心（平台运维） |
| **学生处/德育处** | 德育评价、班级管理、综合素质、行为规范 | 德育管理、班级评价、综合素质、特殊学生库、学生请假 | 宿管科（宿舍行为）、保卫处（进出校记录）、心理中心（心理数据）、年级组（班级管理） |
| **信息中心** | 系统运维、数据管理、账号管理、平台对接 | 基础数据中心、认证管理、数据开放、表单管理、所有第三方对接、流程管理 | **所有科室**（账号/权限/数据支持） |
| **人事处** | 教师档案、考勤、薪资、职称评定 | 人事管理、教师档案、教师考勤、薪资管理 | 教务处（教师课时统计）、财务处（薪资发放） |
| **财务处** | 学费收缴、工资发放、经费管理 | 网上收费、薪资管理、缴费管理 | 人事处（薪资数据）、学生处（学生名单） |
| **后勤/资产处** | 资产管理、耗材采购、教室场地管理 | 资产管理、耗材管理、空间预约、食堂管理 | 信息中心（设备资产）、教务处（教室使用） |
| **保卫处** | 进出校管理、访客登记、安防监控 | 进出校管理、访客管理、视频融合、在线巡查 | 学生处（请假审批联动）、宿管科（归寝联动）、年级组（学生管理） |
| **招生办** | 招生宣传、报名录取、新生报到 | 招生管理、迎新报到 | 信息中心（数据同步）、财务处（缴费） |
| **就业处/实习办** | 实习安排、校企对接、毕业去向 | 实习管理、毕业去向 | 教务处（学分对接）、学生处（学生档案） |
| **督导室** | 教学督导、听评课、质量评估 | 督导评估、教学督导、教师评价 | 教务处（课表/成绩）、教研室（教研数据） |
| **心理中心** | 心理咨询、心理普查、危机干预 | 身心健康、特殊学生库 | 学生处（学生信息）、年级组（班主任反馈） |
| **宿管科** | 宿舍分配、查寝、归寝管理 | 宿舍管理、人脸面板机/宿舍牌 | 学生处（学生信息/请假）、保卫处（进出校）、年级组（班主任查寝） |
| **校办** | 公文流转、会议管理、OA审批 | OA办公、公文管理、会议管理、任务协同 | **所有科室**（公文/流程发起方） |

### 2.4 多科室协同模块的处理规则

当一个模块涉及多个科室时：

| 场景 | 处理方式 |
|------|---------|
| **录入时** | 模块归属到**主要使用科室**下填写，在「协同科室」字段勾选其他参与科室 |
| **查看时** | 该模块在主要科室详页中完整展示，在协同科室详页中以「协同参与」标签简化展示 |
| **编辑时** | 修改该模块状态，主科室和协同科室视图同步更新（同一份数据） |
| **统计时** | 模块只计入主要科室的计数，避免重复计算 |

**前端示意**——宿舍管理模块在宿管科（主要科室）中完整展示，在学生处和保卫处中简化展示：

```

  协同科室：学生处(学生信息共享)、保卫处(归寝联动)、年级组(班主任查寝)

  [📎 素材：3个文件]

【学生处 Tab — 简化展示】
  ─ 协同模块 ─
  ✓ 宿舍管理（协同） · 主科室：宿管科 · 学生信息已对接 → [跳转到宿管科]

  ✓ 宿舍管理（协同） · 主科室：宿管科 · 归寝数据已联动 → [跳转到宿管科]

### 2.5 科室核心数据采集

了解科室业务只是第一步，还需要掌握各科室的**核心数据指标**——这些数据是学校管理决策的依据，也是验证产品落地价值的硬指标。

#### 2.5.1 为什么要采集核心数据

- **量化客户现状**：不只是"排课效率低"，而是"目前排课冲突率约15%，人工处理一次调代课平均耗时30分钟"
- **验证产品效果**：上线前后对比——"课表中心上线后，排课冲突率从15%降至2%，调代课处理时间缩短到5分钟"
- **发现数据孤岛**：哪些数据目前靠人工统计、哪些已有系统但不互通——为后续模块推荐提供依据
- **充实案例素材**：后续产品案例中的数据统计（平均使用率、活跃用户数等）来源于此

#### 2.5.2 各科室典型核心数据

| 科室 | 核心数据指标 | 数据来源（当前） | 能否通过我司模块实现 |
|------|------------|---------------|-------------------|
| **校领导** | 教师出勤率、学生入学率/流失率、信息化经费执行率 | 人工汇总各科室报表 | ✅ 数据大屏自动汇聚 |
| **教务处** | 排课冲突率、调代课次数、考务场次、成绩平均分/标准差、班级课表饱和度 | Excel/纸质/教务系统导出 | ✅ 课表中心+成绩管理+考务管理 |
| **教研室** | 教研活动次数、集体备课参与率、课题申报数、资源上传/下载量 | 人工统计/微信群接龙 | ✅ 集体备课+网络教研+资源中心 |
| **学生处** | 学生出勤率、违纪次数、请假人次、德育活动参与率、综合素质评分 | 班主任手工记录/Excel | ✅ 综合考勤+德育管理+请假系统 |
| **信息中心** | 系统在线率、数据接口调用量、用户活跃度、故障响应时长 | 运维日志/手动巡检 | ✅ 基础数据中心+智能物联+周报巡检 |
| **人事处** | 在编/临聘教师数、学历/职称分布、薪资总额、培训完成率 | Excel/人社局系统 | ✅ 人事管理+教师档案+薪资管理 |
| **财务处** | 学费收缴率、欠费名单、月度收支、工资发放金额 | 财务软件/Excel | ✅ 网上收费+薪资管理 |
| **后勤/资产** | 资产总数/在用率、耗材领用量、教室使用率、食堂消费总额 | 手工台账 | ✅ 资产管理+耗材管理+空间预约 |
| **保卫处** | 日均进出校人数、访客登记量、监控在线率、安全事件数 | 纸质登记/设备自检 | ✅ 进出校管理+访客管理+视频融合 |
| **招生办** | 招生计划数/实招数、录取分数线、报到率、生源地分布 | Excel/上级系统 | ✅ 招生管理+迎新报到 |
| **就业处** | 实习覆盖率、对口就业率、校企合作企业数、毕业生去向分布 | Excel/省就业平台 | ✅ 实习管理+毕业去向 |
| **宿管科** | 床位总数/入住率、归寝率、请假人次、宿舍报修量 | 宿管手工记录 | ✅ 宿舍管理+面板机+归寝计划 |
| **校办** | 公文收发量、会议场次、OA审批效率、督办完成率 | OA/人工 | ✅ OA办公+公文管理+会议管理 |

#### 2.5.3 采集方式

**调研阶段**（工程师走访时手动记录）：
- 问清楚当前数据是怎么来的——人工统计？Excel？已有系统？纸质？
- 记录一个典型周期的数值：如上学期排课冲突有多少次、调代课多少条

**模块上线后**（系统自动产出）：
- 正式使用/试用中的模块自动生成核心数据——使用率、活跃用户、业务指标
- 工程师通过画像详情页可查看数据变化趋势

**前端展示**：
- 画像详情页每个科室 Tab 下新增「核心数据」卡片区
- 已购未用/未购模块的数据标注"数据来源：人工统计（估算值：___）"
- 🟢正式使用/🔵试用中的模块数据标注"数据来源：系统自动统计"，展示趋势小图（本季度 vs 上季度）

#### 2.5.4 数据采集的软件实现

**方案一：模块内置数据看板**（推荐，正式使用/试用中的模块自带统计）
- 课表中心自动统计排课冲突数、调代课处理时长
- 宿舍管理自动统计归寝率、异常人数
- 数据自动同步到画像 `dept_*_metrics` 字段

**方案二：周报沉淀**（模块未启用时的过渡方案）
- 工程师在周报中记录人工统计的核心数据
- 长期积累可生成手工数据趋势线

**方案三：画像手动录入**（灵活补充）
- 直接编辑画像时，科室表单下新增「核心数据」输入区
- 适用场景：模块未上线但需要记录客户当前数据基准线

### 2.6 画像录入/编辑

画像支持三种更新路径，不同路径适用于不同场景：

| 路径 | 入口 | 适用场景 | 操作内容 | 触发版本 |
|------|------|---------|---------|---------|
| **新建画像** | 列表页「+ 新建画像」→ 空白表单 | 首次为学校建档 | 全量填写基础信息+硬件+科室业务+模块状态 ，同时也能通过下载模板导入excel文件。| v1 |
| **直接编辑画像** | 详情页「编辑」按钮 → 预填充表单 | 定期更新（如一个季度后重新走访科室、模块落地状态变更） | 修改任意字段：科室人员/业务/痛点、模块状态/使用率、硬件网络、素材 | v2, v3, v4... |
| **周报录入** | 详情页「本周周报」→ 周报表单 | 日常运维记录 | 每日工作、巡检、宣传、新认知、反馈、问题 | 每次提交生成版本 |

**三者的关系**：
```
新建画像 ──→ 直接编辑 ──→ 直接编辑 ──→ ... (每次生成版本)
               │           │
               └── 周报 ──→ 周报 ──→ 周报 ──→ ... (每次提交生成版本)
```

- 周报是**日常增量**：每周追加工作记录、小范围模块进展
- 直接编辑是**阶段性全量**：季度回访后一次性刷新科室业务描述、批量更新模块状态
- 两者互补：周报数据积累一段时间后，工程师通过直接编辑把周报中的重要变化固化为画像字段

**直接编辑的关键交互**：
- 详情页每个科室 Tab 右上角有「编辑此科室」按钮，支持按科室单独编辑（不一定要改全部）
- 也可通过「编辑画像」进入全量编辑页面（所有科室在同一页）
- 编辑保存后自动生成版本记录，标注修改了哪些科室、哪些模块

### 2.6.1 新建/编辑表单布局

  - 多校区交叉模式下，先选「覆盖范围」：全校共享 or 校区专属

### 2.7 为什么这样设计

科室走访 → 模块匹配 的核心优势：

1. **工程师调研有路径**：不需要面对 101 个模块列表发懵，而是按科室一个一个走，自然覆盖所有模块
2. **业务驱动而非产品驱动**：先理解客户在做什么，再匹配产品，而不是反过来让客户理解我们的产品线
3. **遗漏自检**：每个科室匹配完模块后，如果某个科室没配任何模块，说明这个科室的业务可能还没被我们的产品覆盖

**周报表单结构**（单页，滚动填写）：

| 板块 | 内容 | 字段类型 |
|------|------|----------|
| 诚信声明 | 确认记录真实 | 勾选框 |

**周报去重**：同学校+同工程师+同周报周期只保留一份，重复弹窗确认覆盖。

**关键词**：日清日结 · 有图有真相 · 问题闭环 · 下周计划可追踪

**去重规则**：同学校+同工程师+同周期只保留一份，重复弹窗确认覆盖。

## 四、学校类型适配

### 4.1 作用

不同学校类型的业务场景差异巨大。学校类型适配决定了**哪些科室和模块对该校有意义**：

1. **减少无效工作**：自动隐藏不相关的内容，工程师精力集中在有意义的科室和模块上
2. **提升数据质量**：聚焦该类型学校的核心科室，确保关键数据不遗漏
3. **画像可比性**：同类型学校才有对比意义

### 4.2 科室差异

| 类型 | 缺失/弱化的科室 | 额外/强化的科室 |
|------|----------------|----------------|
| 小学 | 宿管科、招生办、就业处、督导室 | 家校共育（强）、心理中心（强） |
| 初中 | 招生办、就业处、督导室 | +宿管科、德育处 |
| 高中 | 招生办、就业处 | +考务（强）、成绩分析（强）、督导室 |
| 中职 | —（全科室） | +招生办（强）、就业处/实习办（强）、实训室（强） |
| 高职 | —（全科室） | +科研（强）、就业处（强）、教研室（强） |
| K12 | 招生办、就业处、督导室 | 小学+初中合并 |

### 4.3 前端操作

**录入时——校区适配**：
- 选学校类型后，科室列表和模块推荐自动调整
- 若为多校区模式，每个校区可单独设置学校类型（如本部高中+分校初中），各校区按各自类型适配科室和模块
- 硬件区域按校区分组：每个校区独立的硬件表单，全校共享的设施（如网络中心）填在全校层面

**录入时——常规适配**：
- 不存在的科室不展示，不适用模块不推荐
- 小型：自动隐藏宿舍楼栋相关字段；中职额外展示实训室字段

**查看时**：
- 不适用科室不出现，不适用模块灰色标注跳过
- 产品案例筛选按学校类型自动过滤

**编辑时**：
- 学校类型不可修改（类型变更=重新建档）

## 六、版本历史

画像支持版本管理，核心目的是**跟踪学校信息化建设的变化趋势**——例如"半年前该学校只有 5 个模块落地，现在增长到 18 个，信息化等级从初级升至中级"。

每次编辑或周报提交后生成一条记录，存入 `profile_versions` 表：

```
id | profile_id | version_num | changed_fields(JSON) | diff_summary | operator | created_at
```

**趋势分析**：
- 时间轴查看 v1→vN 全链路演变
- 等级变化节点追踪
- 模块增长曲线（通过版本 diff 绘制）
- 点击版本展开变更前后对比

### 调研表与周报在画像中的数据流向

```
调研表（一次性）
  ├─ 基础信息 + 硬件网络 → 画像基础字段
  ├─ 信息化系统建设情况 → 模块状态初始填充
  ├─ 实地勘察 → 硬件/场地字段
  └─ 科室需求 + 走访记录 → 科室业务字段 + 模块匹配

周报（每周持续）
  ├─ 每日工作 + 巡检 → 运维记录，累积到 weekly_reports
  ├─ 应用落地宣传 → 宣传记录（可作为素材补充）
  ├─ 了解客户业务 → 科室业务补充认知，驱动画像字段更新
  ├─ 市场贡献 → 线索记录（助工程师回顾，非画像核心数据）
  └─ 问题 + 计划 → 问题追踪，下周计划

## 十、规则汇总

**核心思路**：科室走访 → 业务理解 → 模块匹配 → 落地追踪 → 画像成型

**数据规则**：单客户单表 · 项目数据自动同步 · 新建全量/编辑增量 · 空值默认「未采集」· 字段溯源标注 · 学校类型过滤科室和模块 · 多校区数据在同一画像内按校区分组存储

**调研表规则**：一次录入覆盖学校全貌 · 校区信息前置采集 · 硬件勘察按校区分组 · 科室标注覆盖范围(全校/校区) · 实地勘察细节不容省略 · 核心数据记录基线

**核心数据规则**：调研时记录数据基线(来源/方式/典型值) · 模块上线后自动统计 · 对比趋势可视化 · 手动+系统双来源标注

**周报规则**：每日记录（非周汇总）· 同周期去重确认覆盖 · 有图有真相 · 问题闭环 · 每次提交生成版本

**素材规则**：🟢正式使用 和 🔵试用中 可上传 · 每模块最多3件 · 降级自动删除 · 提示确认 · OSS存储

**素材规则**：🟢正式使用 和 🔵试用中 可上传 · 每模块最多3件 · 降级自动删除 · 提示确认 · OSS存储

**周报规则**：同周期去重 · 确认覆盖 · 不触发版本历史

**版本规则**：每次编辑或周报提交均生成版本 · 保留全量历史 · 变更前后对比 · 趋势追踪 · 周报版本标注操作类型(编辑/周报)

**产品案例规则**：不新增存储 · 从画像聚合查询 · 降级自动失联 · 支持筛选/统计/对比/导出

**禁止事项**：不碰已有代码和表 · 独立 Schema `design_case_center` · 不删调研字段 · 不做销售分析 · 不覆盖历史数据
